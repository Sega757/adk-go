# Bolt's Performance Journal

## 2026-07-11 - Reflection-based deep copy allocation anti-pattern
**Learning:** Generic reflection-based cloning routines (like `clone` and `deepCopy` in Go) are highly flexible but can be extremely slow and allocation-heavy. Allocating temporary `reflect.Value` instances via `reflect.New` for every struct field or slice element is unnecessary when the destination struct is already fully allocated and its fields/elements are addressable/settable. Direct in-place copying bypasses these allocations completely. Additionally, maps with basic/scalar keys and values do not need deep copying of their keys or values at all, allowing us to skip allocations for map entries entirely.
**Action:** Avoid allocating new values with `reflect.New` for addressable sub-fields or slice elements when implementing generic copy functions. Always check whether the types of keys/values require deep copying (using a helper like `isCopyRequired`) before copying map entries.

## 2026-08-02 - JSON schema conversion and validation fast-path
**Learning:** General-purpose type conversions and schema validations that marshal/unmarshal Go values into raw JSON strings can be extremely slow and allocation-heavy, especially for simple values like strings, float64s, and booleans. When the source and destination types are identical and safe to pass directly to a JSON Schema validation engine, we can bypass the entire JSON serialization pipeline, reducing execution time and allocation overhead significantly. However, care must be taken to only bypass checks on safe primitive types (`string`, `float64`, `bool`, and untyped `nil`) and avoid assertions on typed nil pointers (which would cause runtime type assertion errors or incorrect validation bypass).
**Action:** Always implement a selective fast-path for JSON-safe types during validation and conversion routines to avoid JSON marshal/unmarshal rounds, but ensure other numeric types and pointers continue to fall back to standard deserialization pathways for correctness.

## 2026-08-24 - Lazy map key collection for error reporting
**Learning:** Collecting all map keys into a slice upfront (e.g., using `slices.Collect(maps.Keys(m))`) when preparing metadata for rare error messages causes unnecessary heap allocations and iteration overhead on every normal/happy execution path. Wrapping map key collection in a lazy `sync.Once` closure defers iteration and slice allocations exclusively to the error handling path.
**Action:** When map keys or descriptive string arrays are only consumed in error formatting / fallback paths, use lazy evaluation to eliminate allocations on standard execution paths.

## 2026-09-15 - strings.Builder for multi-chunk streaming transcription aggregation
**Learning:** In event loops that aggregate multi-turn streaming text chunks (such as audio transcriptions), using string concatenation (`+=`) causes $O(N^2)$ repeated memory allocations and heap copying. Replacing string variables with `strings.Builder` (`var sb strings.Builder`) allows continuous chunk appending via `.WriteString()` without intermediate allocations. Calling `.Reset()` clears the internal buffer between events, preventing memory leaks while retaining underlying slice capacity.
**Action:** Always prefer `strings.Builder` over string concatenation (`+=`) when accumulating text chunks across sequential events or loops.

## 2026-10-18 - Lazy set/map allocations and fast-paths in session scans
**Learning:** Functions that scan session history loops (like `findUnresolvedTaskDelegations` in chat-coordinator dispatch loops) frequently allocate tracking maps (`map[string]int` or `map[string]struct{}`) unconditionally at the start of every turn. On normal turns where session history contains zero task delegations, these map allocations create unnecessary heap churn. Lazily allocating tracking sets/maps only when matching `FunctionCall` or `FunctionResponse` items are encountered, combined with fast-paths when no pending calls exist or no responses have been recorded, eliminates heap map allocations and slice allocations entirely on standard turns.
**Action:** Always lazily allocate tracking maps and add zero-allocation fast-paths when scanning session event history for task delegations or function calls.

## 2026-11-09 - Zero-allocation state name validation and string fast-paths
**Learning:** String helper routines invoked during template instruction interpolation (e.g. `isValidStateName`) can create heap allocation overhead if they use `strings.Split` and temporary slice literals (`[]string{...}`) on every variable match. Replacing `strings.Split` with `strings.Cut` and a static `switch` statement achieves zero heap allocations ($0$ B/op). Additionally, template interpolators often use `fmt.Sprintf("%v", value)` generically, incurring interface boxing and reflection allocations even when values are already strings. Adding a type switch fast-path (`case string: return v, nil`) bypasses `fmt.Sprintf` reflection completely.
**Action:** Use `strings.Cut` instead of `strings.Split` when parsing prefixed variable names, and provide type switch fast-paths for string types in template interpolators to avoid `fmt.Sprintf` reflection costs.

## 2026-11-28 - Reflection-free struct zero-value checking for non-comparable types
**Learning:** Using `reflect.ValueOf(*p).IsZero()` to check if a struct pointer (e.g. `*genai.Part`) points to a zero-value struct incurs reflection allocations and CPU overhead on every invocation, especially in hot loops like streaming LLM response aggregation and event history filtering. Because structs containing slice or map fields cannot be directly compared with `==`, developer code often defaults to reflection. Implementing an explicit field-by-field check function (`IsZeroPart(p *genai.Part) bool`) eliminates all reflection overhead, achieving 0 B/op and ~0.45 ns/op performance while also safely handling `nil` pointers.
**Action:** Replace `reflect.ValueOf(*p).IsZero()` on non-comparable structs in hot loops with explicit field-by-field helper functions to achieve zero-allocation ($0$ B/op) zero-value checking.

## 2026-12-15 - Lazy map/slice allocations and fast-paths in LLM history processing
**Learning:** In `internal/llminternal/contents_processor.go`, `rearrangeEventsForFunctionResponsesInHistory` and transcription event aggregation allocated tracking maps (`map[string]int`) and intermediate slices (`[]*session.Event`) unconditionally on every request turn, even when session history contained zero function responses or transcription events. Lazily allocating tracking maps and intermediate slices only when matching events are encountered—and returning original event slices directly when no function responses exist—eliminates map/slice heap allocations and avoids redundant second-pass iterations over history events.
**Action:** Always lazily allocate tracking maps and intermediate slices in LLM context/history processors, and provide fast-path early returns when no matching events exist in history.

## 2027-01-08 - Lazy map allocations and zero-allocation fast-path for state delta extraction
**Learning:** Unconditionally initializing multiple result maps (`appStateDelta`, `userStateDelta`, `sessionStateDelta`) at the start of utility functions that extract sub-state maps incurs up to 3 map heap allocations (~144 B/op) on every event update, even when input state deltas are empty or contain only session-level state. Returning `nil` maps directly on empty inputs achieves 0 B/op (~2.5 ns/op, a ~72x speedup). Lazily instantiating maps only when matching prefixed keys (`app:`, `user:`, session) are encountered eliminates unnecessary map allocations during state processing.
**Action:** Fast-path empty/nil map inputs in state parsing helpers to return `nil` maps with 0 allocations, and lazily allocate categorical maps only upon first key match.

## 2027-01-30 - Zero-allocation fast-path for event response finalization
**Learning:** In LLM event processing loops (such as `finalizeModelResponseEvent`), helper functions like `findLongRunningFunctionCallIDs` are called on every single model turn. Unconditionally allocating tracking sets (`map[string]struct{}`) and collecting keys via iterators (`maps.Keys`/`slices.Collect`) incurs heap map and slice allocations even on text-only turns with zero function calls. Adding a fast-path check `len(fnCalls) == 0` that returns `nil` directly—and using slice accumulation with `slices.Contains` deduplication for the rare cases where function calls exist—eliminates all heap allocations ($0$ B/op, 0 allocs/op) on standard model response turns.
**Action:** Always fast-path empty function call slices before creating set maps or iterators in event finalizers, and prefer slice deduplication over map allocations when processing small collections ($N \le 5$).
